# Working a map: resolve, resume, status, review

This is the procedure `SKILL.md`'s routing section hands off to for the four verbs that operate against an **existing** Map: `resolve <topic-ref>`, `resume [session-or-map]`, `status [map]`, and `review <concern-id>`. It never charts a Map or creates the first Topics — that's [map.md](./map.md). It never runs the interview mechanics from scratch either — `resolve` reuses the direct-session procedure's round shape and persistence rule (`SKILL.md` sections c and d) verbatim, scoped to one Map Topic's Concerns instead of a mapless seed. Every write against a Topic goes through the five operations in whichever backend this Map uses ([local-backend.md](./local-backend.md) or [tracker-backend.md](./tracker-backend.md)) — never an ad hoc `Read`/`Write`/`Edit` of a topic file, or an ad hoc `gh` call.

**Backend-generic throughout.** This file's operation references — `local-backend.md#<anchor>` links, and looser mechanics mentions like "scan `topics/`" — describe the local Markdown backend's concrete implementation of ADR 0002's five topic-store operations (and the claim/frontier checks built on them). Read every one as whichever backend this Map's charting decided ([map.md](./map.md#backend-decision)): [local-backend.md](./local-backend.md)'s mechanics for the local backend, [tracker-backend.md](./tracker-backend.md)'s for the tracker backend. The two files define the same five operations under the same headings and anchors, and tracker-backend.md documents the tracker-backend equivalent of a `topics/` scan (a frontier query scoped to this Map's `resolver: perspec-me` children) — so every reference below resolves correctly either way, without rewriting this file's prose backend-by-backend.

## Session identifier

Per [local-backend.md](./local-backend.md#claim), a session identifier is anything that uniquely names the session — a date-stamped slug is enough for a solo project. Within one conversation, `resolve` mints (or reuses) this identifier once, the first time it claims a Topic, and every later `resolve`/`resume`/status check in that same conversation reuses the same value. A fresh conversation resuming a Topic claimed by an earlier one has no way to recover that identifier on its own — the human must supply it as `resume`'s argument (see below).

## Low-resolution load, everywhere

Every one of these four verbs starts by loading the Map file (`requirements/perspec-me/<map-slug>/MAP.md`) at **low resolution**: read the **Destination**, **Frontier**, and **Blocked** sections (plus **Fog** where a verb needs it), never the full **Decisions so far** history, never every Topic file, and never every Concern Resolution page. Anything beyond that is loaded on demand, scoped to the one Topic or one Concern the verb is actually working — this mirrors the fit decision and charting pass in [map.md](./map.md), which apply the same discipline to reading the catalog.

## Concurrency: one Topic per Session, claim before work

Stated once here because all four verbs touch it in some way. The mechanics below are phrased for the local backend's `topics/` directory scan; on the tracker backend, the same two checks run over this Map's child issues carrying `resolver: perspec-me` instead — assignee for `claimed_by`, the issue's own `concerns:` line for the shared-Concern overlap check, native `blocked_by` for the `blocked_by` check ([tracker-backend.md](./tracker-backend.md)) — same logic, no separate rule.

- A Session that has already claimed a Topic must **resolve** it, **leave it open**, or explicitly hand it off before claiming a different one. Before claiming a new Topic, scan `topics/` for any file that is both `status: open` **and** `claimed_by` equal to this session's own identifier; if one exists and isn't the Topic being claimed, stop and say so instead of claiming a second one. A Topic **record resolution** already closed keeps its old `claimed_by` as historical attribution (per [local-backend.md](./local-backend.md#record-resolution)) — a resolved Topic is never "still claimed" for this check, only an open one is.
- Before claiming a Topic, also check it against every Topic **currently claimed by another session** — scan `topics/` for files that are `status: open` with `claimed_by` set and not equal to this session's identifier (this scan, and the refusal rule on `claim` itself, are documented in [local-backend.md](./local-backend.md#claim)). A resolved Topic is excluded from this scan for the same reason. For each remaining other-claimed-and-open Topic, the target Topic conflicts if:
  - they share any Concern ID (their `concerns` lists intersect), or
  - either names the other in its `blocked_by`.
- On conflict: refuse to claim, name the conflicting Topic (its slug and question) and the reason (shared Concern `<id>`, or the `blocked_by` edge), and stop — no interview round runs.
- On no conflict: run **claim** ([local-backend.md](./local-backend.md#claim)) before any interview round starts, exactly as the direct-session procedure claims nothing today (it has no Topic to claim) but a Map Topic always does.

## `resolve <topic-ref>`

1. **Load the Map at low resolution** (above).
2. **Pick the Topic**: if `<topic-ref>` names one, use it; otherwise take the first entry in **list frontier**'s current result ([local-backend.md](./local-backend.md#list-frontier)) — the Map's rendered Frontier section is that query's last-regenerated snapshot, so prefer re-running **list frontier** live over trusting a stale rendering if the two could differ.
3. **Run the concurrency check and claim** (above) — before any interview work, not after.
4. **Load only this Topic's Concerns**: read the Topic file's `concerns:` list, then for each ID, the Concern's Resolution page under `requirements/perspec-me/<map-slug>/concerns/<concern-id>.md` (if one already exists) and its canonical catalog page. Nothing else — no other Topic's Concerns, no other Concern Resolution pages.
5. **Investigate + interview**: reuse `SKILL.md` section b (investigate) and section c (the six-part round) exactly as written, scoped to this Topic's question and Concerns instead of a mapless seed. Reuse section d's persistence rule exactly — write to `requirements/perspec-me/<map-slug>/concerns/<concern-id>.md` (the Map's Concern Resolution path, per [map.md](./map.md#resolution-layer-convention-once-a-map-exists)), never `_unmapped/`, after every answer. Do not re-describe the round shape or the persistence rule here — the six parts and the per-answer rule are section c/d's job, cited, not duplicated.

### New-question classification

Whenever a round surfaces a question beyond the one currently being resolved, classify it into exactly one of these four outcomes — never leave it unclassified or silently dropped:

- **Small and inseparable** — folds into the current Topic's remaining questions; it does not become a new Topic, a Fog entry, or an Out-of-scope line. Keep resolving it as part of this Topic.
- **Distinct and formulable** — precise enough to state as its own question. Run **create topic** ([local-backend.md](./local-backend.md#create-topic)) for it now, with `wire blockers` ([local-backend.md](./local-backend.md#wire-blockers)) if it depends on something already known. If it has no blockers (or all its blockers are already resolved), it is on the Frontier the moment it's created — that's just what **list frontier** computes over the directory, not a separate edit.
- **Known but nebulous** — real and relevant, but not yet phraseable as a precise question. Add one Fog entry to the Map's Fog section, per [map.md](./map.md#fog)'s shape (label, Perspective/task, one or two lines).
- **Beyond the destination** — outside what this Map's Destination covers. Add one line to the Map's **Out of scope** section with a one-line reason. Never drop it silently — a reader must be able to see it was considered and excluded on purpose.

**Fog graduation**: the moment a Fog entry becomes precise enough to state as a question — whether that happens mid-`resolve` on the current Topic or on an unrelated one — remove it from the Map's Fog section and run **create topic** for it in the same edit. This is [map.md](./map.md#hard-invariant)'s Hard invariant applied during `resolve`, not a competing rule: the same understanding never sits in both Fog and a Topic file at once, even briefly across two writes.

### Closure

When the Topic's question is settled and the user agrees it's resolved, these four things happen together, in one closing pass — not staggered across separate steps:

1. **Record resolution** ([local-backend.md](./local-backend.md#record-resolution)) — sets the Topic file's `status: resolved` and `resolved_at`, appends the decision line to the Map's Decisions so far, and creates/updates the touched Concern Resolution page(s).
2. The Topic **leaves the Frontier automatically** — **list frontier** no longer selects a `resolved` Topic, so this is not a separate edit.
3. Any Topic that named this one in its `blocked_by` is **unblocked** — the next **list frontier** run reflects that automatically on the data side, but explicitly **refresh the Map's rendered Frontier and Blocked sections** so a human reading the Map file sees the newly-unblocked Topic move over, not just the underlying directory state.
4. **Refresh the Map's Perspective resolution coverage table** ([map.md](./map.md#the-map-file)) for the Perspective(s) the touched Concern(s) belong to, from those Concerns' current `status`.

Also publish a short synthesis on the Topic (what was decided, which Concerns/Resolution pages were touched) as part of this same pass, the same shape the direct-session procedure's closure already produces (`SKILL.md` section e) — closing a Topic under a Map still never begins implementation.

### Alternative outcomes

- **Left open**: the session ends without the Topic reaching closure. Do not call **record resolution** — the Topic file stays `status: open` and still `claimed_by` this session. A later session either resumes it (see `resume` below, run by the same session identifier or a human-supplied one) or the claim eventually needs releasing; this ticket does not build an explicit "unclaim" step — note it as a gap for whichever future ticket needs it, don't invent one here.
- **Split**: a Topic that has grown past what one session can hold.

  **Recognizing the signal.** The trigger is the issue's own test — "the question cannot be settled without materially expanding the session" — made concrete against the six-part round (`SKILL.md` section c). Either of these, mid-round, is the signal:
  - Part 1's **current understanding** can no longer be written as one coherent 2-5-line summary without conflating two or more threads that don't share an answer — you find yourself reaching for "separately," "meanwhile," or a bulleted list of unrelated threads just to say where the Topic stands.
  - Part 2's **question being resolved** has turned out to be several genuinely independent sub-questions — answering one doesn't move the others forward, and different stakeholders could plausibly answer them on different timelines. This is the same test `map.md`'s fit-in-one-session decision applies before a Map exists, applied here mid-session to one Topic that's already past charting.

  Either symptom triggers *proposing* a split, never doing it silently. State the proposed split to the user — the tentative set of independent questions you'd carve out — and wait for explicit confirmation, the same Destination-confirmation-gate discipline `map.md` uses before any Topic exists: no **create topic** call runs before the user agrees. If the user declines, the session continues the interview on the original Topic as a single Topic — nothing is created, nothing about its file changes.

  Once the user confirms, in one pass:

  1. **Preserve decisions so far, before doing anything else.** Write a short synthesis into the original Topic's own Notes — what's already settled — the same shape as the direct-session procedure's closure synthesis (`SKILL.md` section e: what was decided, which Concerns/Resolution pages were touched). This doesn't touch Concern Resolution pages themselves — those already hold whatever was persisted per answer (`SKILL.md` section d); this synthesis is the Topic file's own record of where it stood at split time.
  2. **Identify the independent questions that remain — split by question or decision, never by Concern.** A Topic touching four Concerns does not automatically become four new Topics: the number of new Topics is however many genuinely independent questions remain, which may be fewer, or occasionally more, than the number of Concerns touched. Apply the same charting discipline `map.md` uses when charting a Map: only split off a question that's already precisely phraseable now; a thread that's real but not yet sharp enough to state as a question is Fog, not a new Topic (step 5).
  3. **Create the new Topics.** For each remaining independent question, run **create topic** ([local-backend.md](./local-backend.md#create-topic)), phrased as a question, with `concerns:` set to whichever Concern IDs it plausibly touches. A Concern may be relevant to more than one new Topic — that's the normal N:N shape (`CONTEXT.md`), not a sign the split is wrong.
  4. **Wire dependencies between the new Topics.** Where one new Topic's answer plausibly constrains another's, run **wire blockers** ([local-backend.md](./local-backend.md#wire-blockers)) on the dependent one — only wire what's already apparent from the split, the same restraint `map.md`'s Dependencies section uses; don't speculate a blocker to look thorough.
  5. **Route any leftover Fog or out-of-scope material** the split surfaces through the existing mechanics, unchanged: a region that's relevant but not yet phraseable as one of the new Topics becomes a Fog entry (`map.md`'s Fog section); a thread beyond this Map's Destination becomes a line in Out of scope — never dropped silently, same as the New-question classification above.
  6. **Turn the original Topic into an aggregator.** Do not run **record resolution** on it — an aggregator's question was divided, not answered, so it never carries `resolved_at`. Set its `children:` field (see [local-backend.md](./local-backend.md#topic-file-shape)) to the new Topics' slugs; this is the only write that ever populates `children:`. Its `status` stays `open` and its `claimed_by` stays whatever the concurrency check set when this session claimed it — an aggregator is not a third status value, it's an open, still-claimed Topic that happens to have children, which is exactly why it needs no special case to stay off the Frontier (next step).
  7. **The new Topics land on the Frontier exactly as usual.** An unblocked new Topic (no `blocked_by`, or every named blocker already resolved) is on the Frontier the moment it's created — that's just what **list frontier** ([local-backend.md](./local-backend.md#list-frontier)) computes over the directory, the same restatement the "Distinct and formulable" classification above already gives a newly-created Topic, not a separate mechanism for split-created ones.
  8. **End the session.** The split is where this session stops — no further interview rounds run against the now-split Topic in this session. A later `resolve` against one of the new Topics is a new claim, same as any other Frontier Topic.
  9. **Refresh the Map.** The Map's rendered Frontier and Blocked sections pick up the new Topics on next read/update — the same "regenerate, don't hand-edit" rule as the closure section above and `map.md`'s Frontier section. Any Fog or Out-of-scope lines from step 5 are already reflected, since they were written directly into the Map's own sections.

  A later reader landing on the aggregator Topic finds every child from its `children:` list.

  **On the tracker backend:** the same split runs against [tracker-backend.md](./tracker-backend.md)'s operations instead of local-backend.md's. Steps 3-4 above become: **create topic** for each remaining independent question (a new child issue of the Wayfinder map, each with its own `resolver: perspec-me` and `concerns:` — never one child issue per Concern), then **wire blockers** for any apparent dependency between them (native `blocked_by` edges, [tracker-backend.md](./tracker-backend.md#wire-blockers)). Step 6 changes shape: GitHub issues carry no `children:` frontmatter field, so — per issue #17's own aggregator rule, applied through this backend's own remote-write discipline ([tracker-backend.md](./tracker-backend.md#remote-write-discipline)) — the original issue stays open, keeps whatever assignee it already had, and gets a **comment** (an allowed write) listing the new child issues as a checklist of links, rather than an edit to its own body (editing a ticket's body after creation sits outside the four writes this backend performs without explicit authorization). The original issue is never passed to **record resolution** — divided, not answered, same as the local backend. Steps 7-9 hold unchanged: the new issues land on this backend's **list frontier** the moment they're created and unblocked, and a later reader finds every child from that same aggregator comment.

- **Blocked on delegated work**: the question can't be answered by interview alone — see [Delegated work](#delegated-work) below.

## Delegated work

Some questions a round surfaces cannot be settled by interviewing the user, no matter how many rounds run — an external fact is missing, the conversation genuinely cannot decide how something should look or behave, or someone has to go do something manual before a decision is possible. When a round hits one, it records **Delegated work** ([CONTEXT.md](./CONTEXT.md)'s definition) on the Map instead of guessing, links it from the blocked Topic, and the Topic moves to Blocked as a direct consequence. This is a fourth alternative outcome for `resolve`, alongside Left open and Split above — never something a session fakes an answer to avoid.

### Classifying the question

Exactly one of three types, using the issue's own test — never left unclassified:

- **Research** — an external fact blocks the decision: a regulation, a technology's actual capability or limit, a benchmark, published literature, a third-party service's cost or SLA. The fact exists somewhere outside this conversation; the work is finding it.
- **Prototype** — the conversation cannot decide how something should look or behave, and a working artifact would settle it faster than more discussion (a state model that's hard to reason about on paper, a UI shape no one can agree on in the abstract). The prototype answers this one question — it is never the product, and building it never counts as starting implementation.
- **Unblocking task** — manual work has to happen before a decision is possible, and no amount of research or prototyping substitutes for it: getting access to a system, pulling a data sample, running a small exploratory experiment, having a stakeholder conversation that only a human can have.

If more than one type seems to apply, pick the one whose result is the actual blocker — e.g. if the plan is "run a benchmark, then decide," the missing benchmark result is Research even though someone has to go run it; the task itself is the vehicle, not a separate Unblocking task, unless getting to a position to run it (e.g. provisioning access) is itself the blocking step, in which case that access is its own Unblocking task and the benchmark is a Research entry that depends on it (`blocked_by` the Unblocking task's Topic-side entry, once both exist).

### Creating the entry and blocking the Topic

1. **Create the Delegated-work entry** directly in the Map file's own **Delegated work** section, using the `dw-<slug>` shape defined in [map.md](./map.md#the-map-file): a stable ID, its `type`, the `question` it exists to answer (stated as precisely as the Topic's own question would be), `blocks: <topic-slug>`, `status: pending`, `created_at`. This is a direct edit to the Map file, not a sixth topic-store operation — Delegated work is a Map-level record, not a Topic, the same way Fog entries and Out-of-scope lines are already written directly into the Map's own sections rather than through one of the five topic-store operations ([local-backend.md](./local-backend.md#where-things-live)).
2. **Link it from the Topic, and release the claim, in the same edit.** Run **wire blockers** ([local-backend.md](./local-backend.md#wire-blockers)) on the blocked Topic, appending `dw:<delegated-work-id>` to its `blocked_by` list — the same operation Split and ordinary Topic-to-Topic dependencies use, just naming a Delegated-work entry instead of a topic-slug (per [local-backend.md](./local-backend.md#topic-file-shape)'s `blocked_by` convention). In the same write, clear the Topic's `claimed_by` back to empty — the one narrow exception to "claimed_by is never cleared once set" ([local-backend.md](./local-backend.md#claim)): a Topic blocked on Delegated work has nothing left for this session to do until the delegated work resolves, and leaving the claim in place would stop the Topic from returning to the Frontier automatically later (below), the same way a `Left open` Topic's retained claim deliberately keeps it off the Frontier for anyone but the claiming session.
3. **The Topic is now Blocked — no further edit needed.** Once the `dw:` entry is wired and the claim cleared, **list frontier** ([local-backend.md](./local-backend.md#list-frontier)) no longer selects this Topic — its second condition fails (the named Delegated-work entry is `pending`, not `resolved`) even though its third condition (claim cleared) now passes — so the Topic stops appearing on the Frontier and starts appearing in Blocked the next time either is read or regenerated. This is the same "recompute, don't hand-edit" discipline as every other Frontier/Blocked transition in this file — there is no separate "mark this Topic Blocked" step.
4. **End the round on this question.** The session does not keep interviewing toward an answer the delegated work hasn't returned yet; it reports the entry it created and moves to another Frontier Topic, or ends. Because the claim was released in step 2, a *different* session may pick this Topic straight off the Frontier the moment it unblocks — resolving Delegated work is not reserved to the session that created the entry.

### Resolving Research and Prototype entries

For a `research` or `prototype` entry, resolve it by calling the Skill tool with the matching skill — one call per entry, one skill per call, per [.agents/invocation.md](../../../.agents/invocation.md):

- **Research** — call the Skill tool with `"research"`. Hand it the entry's `question` plus enough context to keep it scoped: the Topic's current understanding, the Concern(s) it's expected to bear on, and any evidence already on record in those Concerns' Resolution pages. `research`'s own procedure ([skills/engineering/research/SKILL.md](../../engineering/research/SKILL.md)) spins up a background agent that investigates against primary sources and writes its findings to a Markdown file, citing each claim's source — that file **is** the answer plus evidence plus sources; perspec-me's own job, once it comes back, is to read that file and determine which of this Map's Concerns it actually affects and whether it surfaces any new Topic-worthy questions (`research` itself has no notion of a Concern or a Topic — that translation is this skill's, not `research`'s).
- **Prototype** — call the Skill tool with `"prototype"`. Hand it the entry's `question` and enough surrounding context (the relevant code or design area, the state model or UI shape in question) for `prototype`'s own branch-picking step ([skills/engineering/prototype/SKILL.md](../../engineering/prototype/SKILL.md)) to choose LOGIC vs UI correctly. `prototype` returns a validated decision folded into real code, plus the throwaway prototype itself committed to its own branch with a context pointer — normally left "on the implementation issue," which doesn't exist here, so perspec-me leaves that context pointer on the Delegated-work entry itself (its `result.evidence`, below) and on the blocked Topic's Notes instead. The verdict — what the prototype settled — is the answer; the branch and commit are the evidence and sources.

Mark the entry `status: in-progress` for the duration of the call (a reader mid-flight should see it's not idle).

### Resolving Unblocking-task entries

No Skill tool call — this is manual work only a human can do. Instead, write the entry's `checklist` (per [map.md](./map.md#the-map-file)'s shape) as a precise, human-actionable list: one item per concrete action, never a vague catch-all. "Investigate further" is not a checklist item; "get read access to the events warehouse," "obtain a de-identified sample of the last 30 days of checkout events," and "schedule a 30-minute conversation with the payments lead about chargeback handling" are. Hand the checklist to the user as part of the round's report and mark the entry `status: in-progress` once they've acknowledged it. The human reports back when it's done (or partly done); there is no automated completion signal for this type.

### When a delegated result returns

Whichever type it was, write the result back through the existing persistence mechanics — this reuses `SKILL.md` section d's create-once/append-after rule verbatim, it does not invent a new one:

1. **Update the Delegated-work entry itself**: set `status: resolved`, `resolved_at`, and fill in `result` — `answer`, `evidence`, `sources`, `affected_concerns` (the Concern IDs this result actually bears on), and `new_topics` (any newly discovered Topic-worthy questions the result surfaced, or empty).
2. **The blocked Topic returns to the Frontier automatically.** Nothing is deleted from the Topic's `blocked_by` list — the `dw:<id>` entry stays, permanently, exactly as a resolved Topic-to-Topic blocker stays in `blocked_by` after that Topic resolves ([local-backend.md](./local-backend.md#topic-file-shape)). Because the named entry's own `status` is now `resolved`, **list frontier**'s second condition is satisfied; its third condition (claim cleared) has already been satisfied since the Topic was blocked (above); so the next read of the Frontier picks the Topic back up on its own — no separate "unblock" write, and no claim to clear at this point since that already happened when the Topic became Blocked. Fold the delegated answer into the Topic's own Notes so its next round has it as context, the same way any other evidence gathered mid-Topic gets folded in ([SKILL.md](./SKILL.md) section b).
3. **Update each affected Concern's Resolution page** named in `affected_concerns` — same create-once/append-after rule as an interview answer (`SKILL.md` section d): create the page only if this is the first time this Map's Topics have touched that Concern, otherwise append. Add the delegated work's `evidence`/`sources` to that page's own **Evidence** section, and a line to **Topic history** noting the Delegated-work entry (by ID) that contributed it.
4. **Route any `new_topics` through the existing classification, unchanged.** A newly discovered Topic-worthy question from a delegated result is not a special case — run it through the same [New-question classification](#new-question-classification) above: **create topic** if it's already phraseable (with `wire blockers` if it depends on something known), a Fog entry if it's real but not yet sharp, or an Out-of-scope line if it falls outside this Map's Destination. Never invent a second classification scheme for delegated-result questions.
5. **Refresh the Map's rendered Frontier, Blocked, and Delegated-work sections** in the same pass — the same "regenerate, don't hand-edit" discipline as every other closure/split/unblock moment in this file.

### Parallelism: when independent Research may run concurrently

Independent Research delegations may run in parallel — multiple Skill tool calls to `"research"` (each is still one skill per call), or multiple background agents, since `research`'s own procedure already spins up a background agent per call — but **only when the Map marks it safe**, never by default.

**The safety check is the exact same overlap check the concurrency section above already uses for claiming Topics** ([Concurrency: one Topic per Session, claim before work](#concurrency-one-topic-per-session-claim-before-work)) — reused verbatim, not reinvented and not extended. Two Delegated-work entries are safe to run in parallel if and only if their `blocks` Topics do **not** conflict by that same test: they don't share any Concern ID (their `concerns` lists don't intersect), and neither names the other in its `blocked_by`. Any conflict on either count — same as a claim conflict — means not safe.

Compute this once, when the second of the two entries is created (or whenever both already exist and a session is about to run them together), and **record the determination on both entries' `parallel_safe_with` field** ([map.md](./map.md#the-map-file)) rather than re-deriving it fresh every time someone looks at the Map. An entry with nothing in `parallel_safe_with` has not been checked against anything yet (or was checked and found unsafe) — treat it as not safe to parallelize until a check says otherwise. Prototype and Unblocking-task entries are not covered by this rule: a Prototype's artifact-building and an Unblocking task's human legwork aren't parallelized by this mechanic (nothing stops a human from doing their own task alongside a background research agent, but that's outside what this skill schedules).

## `resume [session-or-map]`

1. **Load the Map at low resolution** (above). If the optional argument names an existing `requirements/perspec-me/<arg>/MAP.md`, treat it as a map-slug and load that Map; otherwise treat it as a session identifier (see below). With no argument: if exactly one Map exists under `requirements/perspec-me/`, use it; if more than one, ask which.
2. **State the Destination** — one line, read verbatim from the Map's Destination section.
3. **Summarize recent Decisions so far** — the most recent 3-5 entries from that section, not the entire history.
4. **Show the current Frontier** — the Map's rendered Frontier section (or a fresh **list frontier** run if it looks stale).
5. **Find the claimed Topic**: scan `topics/` for the file whose `claimed_by` equals the session identifier — this conversation's own identifier if `resolve` already claimed something earlier in the same conversation, or the argument the human supplied if this is a fresh conversation resuming an earlier one's claim. Do not ask the user to name which Topic; the claim is what answers that.
6. **Load only that Topic's Concerns** — same restriction as `resolve` step 4.
7. **Continue from the next open question** — use the Topic's own persisted evidence (its Concern Resolution pages' Confirmed facts / Decisions / Open questions, and the Topic file's Notes) to determine what's already answered. Do not re-ask a question that evidence shows was already answered, and do not restart the round sequence from round 1 — pick up mid-round at the next open question, continuing to reuse `SKILL.md` sections c and d exactly as `resolve` does.

**What `resume` must not load**: any Topic file with `status: resolved` (closed Topics), and Concern Resolution pages for Concerns outside the currently-claimed Topic's own `concerns:` list. Both are outside what a resumed Session needs to keep going.

## `status [map]`

Print, from the Map's own sections:

- **Destination**
- **Perspective resolution** coverage table
- **Frontier**
- **Blocked**
- **Fog**
- **Delegated work**
- **Handoff readiness** — per [map.md](./map.md#the-map-file)'s template, recomputed fresh each time this verb runs, the same "regenerate, don't hand-edit" discipline as Frontier/Blocked — never just the last-written rendering trusted at face value:
  1. **Destination reached**, **Fog empty**, and **no material Frontier/Blocked Topic** — read straight off the Destination, Fog, Frontier, and Blocked sections already printed above; no extra file needs opening for these three. "Relevant" Fog excludes anything already given its own line in Out of scope. A remaining Frontier/Blocked Topic only stops counting against completion once the user has explicitly waved it off as non-material, recorded on the Map (a line in Handoff readiness or Decisions so far) — `status` never makes that call unilaterally; an open Topic nobody has explicitly waved off always counts against completion.
  2. **Every relevant Concern `resolved`/`deferred`/`not-applicable` — hard gate.** From the Perspective resolution table's counts, any Concern still `unexamined`/`open`/`partial` fails this outright, named by ID. For every Concern currently `deferred` or `not-applicable`, open that one Concern's Resolution page — scoped to its "Current resolution" section only — and confirm it carries a justification (`SKILL.md` section d's hard rule, extended to `deferred` for the same reason). A Concern missing one blocks completion outright; name it by ID (e.g. "d16-golden-dataset: not-applicable, no justification"). This is the one point where `status` reads beyond the Map file itself, and only the specific pages this check needs — never every page under `concerns/`.
  3. **Contradictions between Concern resolutions — hard gate.** Among the Resolution pages opened for step 2 (or opened on demand here if a contradiction is suspected outside that set), check for two pages, or two Topics' recorded decisions, stating incompatible things about a shared Concern or an overlapping requirement. This is a mechanical check run every time completion is being assessed, never smoothed over silently. An unresolved one blocks completion exactly like a missing justification — name both sides. One the user has already explicitly accepted as tolerable (recorded as its own line in Decisions so far) does not block completion, but must still be named as accepted, not omitted from the report.
  4. **User confirmation — always human-only, never inferred.** Read Handoff readiness's own recorded confirmation line (e.g. "confirmed complete by <name>, <date>"). Absent, this alone blocks completion regardless of how every other criterion looks — a later `status` call has nowhere else to find this fact, since it is never inferred from the state of the other criteria.

  **Reporting the result:**
  - **Complete** (every criterion above holds, including a confirmation line already recorded from this or an earlier session): state plainly that the Map is complete, and **tell the user to run `to-spec`** — phrased exactly as an instruction to the human, never as a Skill tool call. `to-spec` is user-invoked; per [.agents/invocation.md](../../../.agents/invocation.md), no skill — this one included — may reach a user-invoked skill through the Skill tool, however tempting it is to just call it here. Handing off is the last thing this verb does; it never itself opens or edits anything outside this Map's own files.
  - **Incomplete**: name exactly what's blocking completion — which of the six criteria above don't hold, and for the Concern-justification and contradiction gates specifically, the exact Concern ID(s) or the specific pages/Topics in conflict, never a vague "some concerns need work."

This still never opens a Topic file, and opens a Concern Resolution page only when steps 2 or 3 above require it (scoped to the pages the completion check actually needs, not a blanket read of `concerns/`) — the rest of `status`'s output stays a read of the Map file's own sections, verbatim or lightly rendered, as before. Reaching or reporting completion never produces or edits product code — the Map/Topic/Resolution-page files under `requirements/perspec-me/<map-slug>/` are the only artifacts this verb, or any part of `perspec-me`, ever writes. The optional `[map]` argument selects which Map when a project has more than one, the same map-slug resolution `resume` uses in its step 1.

## `review <concern-id>`

Open exactly one file: `requirements/perspec-me/<map-slug>/concerns/<concern-id>.md`. Show its **current resolution**, its `status`, and the **Topic history** section (which Topics shaped it, and what each settled). This does not open the Map file's Decisions-so-far history, any Topic file, or any other Concern's Resolution page — one page in, one page shown.
